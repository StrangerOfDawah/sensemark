# Принятые решения

## D-001 — Никаких правил для конкретных сайтов

Нельзя ветвиться по hostname, URL, title, CSS-классу, точному селектору, имени
шрифта или нестандартному `data-*`. Надёжность достигается стандартными
Selection/Range/accessibility API, оценкой кандидатов и строгими лимитами.

## D-002 — Native first, fallback bounded

Обычное выделение и формы должны завершаться за fast path. DOM-wide traversal
запрещён. Fallback касается только текущего Range, максимум 2000 узлов, 25 мс,
5000 кодовых точек и стандартных семантических полей. Visibility кэшируется,
а кандидат обязан пройти confidence threshold.

## D-003 — Один translation request, без repair

`text` использует plain-text stream. `contextual` и `multilingual` используют
strict Structured Outputs. Неожиданный формат становится явной ошибкой; второй
запрос для ремонта запрещён. Один retry допустим только до первой дельты для
сетевой ошибки, 408/409, короткого 429 `Retry-After` или 5xx.

## D-004 — Provider boundary заранее, второй provider потом

Registry принимает provider с `id`, `displayName`, `capabilities`,
`validateConfiguration`, `translate`, `normalizeError` и
`settingsDescriptor`. OpenAI —
единственная активная реализация и единственный host permission. Исследование
Gemini подтвердило совместимость общего контракта, но не является основанием
добавлять лишний provider или permission сейчас.

## D-005 — Private/public settings

API‑ключ никогда не доступен content script. Trusted extension pages работают с
private settings через service worker; страница получает только selection/ui.
Миграция schema v3 сохраняет старый ключ, модель, поведение и размеры, но
сбрасывает устаревшее privacy consent после изменения disclosure.

## D-006 — Session cache вместо service-worker memory

MV3 может остановить worker в любой момент. Cache хранится в
`chrome.storage.session`, ключ хэшируется SHA‑256, применяется TTL/LRU и лимит
размера. Cache identity включает prompt/protocol/semantic versions; обычный hit
не перезаписывает весь session object немедленно. Cache не является
пользовательской историей переводов.

## D-007 — Intent — отдельная state machine

`pointerdown/up`, keyboard selection и `selectionchange` — сигналы, а не
немедленные команды. Выделение перечитывается после 600 мс и сверяется по
text/source/rect/frame key; duplicate cooldown равен 1500 мс. Copy shortcut и
событие `copy` отменяют только pending intent и не закрывают карточку. Новая
установка использует режим `automatic`: пользователь выделяет текст — перевод
появляется сам, без дополнительного жеста и без модификатора.

## D-026 — Компактная плавающая карточка остаётся основным интерфейсом

Основной интерфейс — компактная плавающая карточка рядом с выделением, как в 1.3.
Карточка имеет ширину по содержимому (230–400px), а не фиксированный блок, и
закрывается по клику вне её пределов. Side panel — только запасной вариант для
контекстов, где карточка технически невозможна (встроенный PDF-просмотрщик,
`chrome://`, Web Store). Обычные страницы никогда не переводятся через панель.

Обязательный модификатор удалён из настроек. Поле `requiredModifier` сохраняется
в схеме со значением `none` только ради совместимости старых профилей.

## D-027 — Структурированный ответ никогда не показывается как JSON

Модель может ответить структурированным JSON на text-mode запрос. Общий
`displayText()` извлекает пользовательский текст из строки-JSON, объекта или
массива и применяется во всех местах вывода, включая поток дельт. Если извлечь
нечего — показывается пустота, но не payload. Обычный текст, начинающийся со
скобки, не считается JSON и отображается как есть.

## D-008 — Карточка управляется пользователем

Placement использует flip/shift/clamp. Header перетаскивается Pointer Events с
pointer capture и rAF; double click возвращает к anchor. Положение после drag не
переопределяется stream-дельтами. Размер и масштаб сохраняются, абсолютная
координата — нет.

## D-009 — Защищённые страницы не считаются ошибкой пользователя

Если content script недоступен, context-menu text временно сохраняется в
tab/frame/request-specific session entry и открывается tab-specific side panel.
Русский и password-source не открывают fallback. Popup остаётся универсальным
ручным fallback.

## D-011 — Русский пропускается только при высокой уверенности

Письменность не равна языку. Запрос блокируется только при reliable `ru` от
Chrome без отрицательного языкового сигнала. При сомнении перевод выполняется;
отдельный LLM-запрос для language detection запрещён.

## D-012 — Завершённость stream является частью протокола

Непустого текста недостаточно. Успех требует `finish_reason: stop` и `[DONE]`.
Length, content filter, прерванный stream и неизвестная причина завершения
остаются разными ошибками и не запускают repair/retry после первой дельты.

То же правило применяется к contextual и multilingual Structured Outputs:
JSON результата разбирается только после `finish_reason: stop`.

## D-013 — Capability validation не равна существованию модели

`GET /v1/models/{model}` подтверждает credentials и видимость модели, но не
Chat Completions, streaming или strict Structured Outputs. Sensemark показывает
`verified` только для provider allowlist; существующая custom model остаётся
`unverified` до реального перевода.

## D-014 — Side-panel handoff одноразовый, но не называется атомарным

Session entry удаляется при claim, а in-memory guard не даёт двум одновременным
consumer начать один перевод. После перезапуска worker durable remove остаётся
источником истины.

## D-017 — Доставка в side panel не зависит от порядка асинхронных операций

Идентичность запроса не передаётся в URL панели. Intent регистрируется
синхронно до первого `await`, поэтому панель, готовая раньше записи в storage,
получает `waiting`, а не пустой результат. Доставка идёт через push от worker и
ограниченные повторы (2 с, шаг 150 мс). Unbounded polling запрещён. Потерянный
handoff обязан завершиться видимой ошибкой, а не пустой панелью.

## D-018 — User activation важнее лишней проверки русского языка

`sidePanel.open()` должен вызываться на стеке пользовательского жеста. Любой
`await` перед ним рискует потерять transient user activation, поэтому
асинхронный `chrome.i18n.detectLanguage()` больше не выполняется до открытия.

Выбран вариант A: синхронный консервативный вердикт. **Ни один отдельный символ
и ни один маленький класс символов не даёт уверенного вердикта**: `ы`, `э` и `ё`
встречаются в казахском, белорусском, киргизском и монгольском. Ранняя версия,
доверявшая этим буквам, ошибочно пропускала «Сынып», «Добры дзень»,
«Кыргыз тили», «Бул жакшы», «Энэ текст» и «Мына сынып».

«russian» требует одновременно: отсутствия non-Russian сигналов, отсутствия
смешанных языковых групп, минимум 16 кириллических кодовых точек, минимум 3
кириллических слов и минимум 2 различных русских служебных слов. Всё остальное —
«uncertain», панель открывается. Короткая кириллица всегда «uncertain».

Приоритет: не потерять валидный нерусский запрос важнее, чем избежать лишней
панели для русского текста.

## D-019 — Замена запроса в одной вкладке атомарна и переживает перезапуск worker

`store()` с последующим независимым `supersede()` допускал чередование
store(A), store(B), A-удаляет-B, B-удаляет-A — оба запроса терялись.

Замена выполняется одной атомарной операцией `state.replace()` под per-tab
блокировкой. Порядок — `(generationId, sequence, createdAt)`:

- `sequence` назначается синхронно в `prepare()` в порядке действий
  пользователя и упорядочивает запросы **внутри** одного поколения worker;
- `generationId` — **durable** счётчик в `chrome.storage.session`, выделяемый
  один раз на экземпляр worker, и он доминирует в сравнении.

Доминирование поколения обязательно: MV3 перезапускает worker и сбрасывает
in-memory счётчик. Свежее действие пользователя начинается с `sequence = 1` и
иначе проиграло бы устаревшей записи, дошедшей до `sequence = 5` в предыдущем
поколении, — клик пользователя был бы отброшен, а панель перевела бы старый
текст.

Внутри блокировки проигравший более старый запрос отказывается сохраняться и не
удаляет победителя. Пока новый запрос уже анонсирован, но ещё не записан, панель
получает `waiting`, а не устаревшую запись с диска.

Активный перевод вытесняется через существующий request coordinator, поэтому
устаревший результат не может заменить новый.

## D-022 — Записи binding сериализованы и упорядочены

Fire-and-forget записи binding могли завершиться не по порядку, и сохранённый
binding указывал на более старую вкладку; после перезапуска worker
восстанавливал неверную идентичность.

Записи сериализованы per-window и упорядочены по
`(generationId, bindingRevision, createdAt)`; запись отказывается перезаписывать
более новый binding. `announce()` возвращает durable-запись как
`intent.persisted`, контроллер включает её в post-open lifecycle, поэтому
handoff не считается подготовленным, пока запись не завершена. Ошибка записи
типизирована, а устаревшему сохранённому binding больше не доверяют.

## D-023 — Асинхронный сбой content script не гарантирует user activation

Маршрут выбирается синхронно по URL вкладки. Известные защищённые контексты
(встроенный PDF-просмотрщик, restricted-схемы, Web Store, нечитаемый URL)
открывают панель немедленно, без единого `await` перед `open()`.

Для обычных страниц сначала выполняется доставка в content script. Сбой после
уже выполненного `await tabs.sendMessage()` **не** приводит к тихому вызову
`sidePanel.open()`: transient user activation могла истечь, вызов бы не
сработал, и пользователь не увидел бы ничего. Запрос завершается как
`CONTENT_SCRIPT_UNAVAILABLE`, а иконка расширения показывает подсказку повторить
команду. Дополнительных разрешений не требуется.

## D-020 — Панель tab-specific, а конфигурация вынесена из пути жеста

Модель панели — **tab-specific**, не global. Вкладки настраиваются на
`tabs.onActivated`, `tabs.onUpdated`, `runtime.onInstalled` и
`runtime.onStartup`, никогда — в обработчике context menu. На пути
пользовательского действия остаётся единственный вызов `sidePanel.open()`.

Три вида отказа различаются: сбой конфигурации не является сбоем открытия и не
удаляет pending; сбой открытия при уже подключённой панели не удаляет pending;
сбой handoff показывается в панели как ошибка.

## D-021 — Идентичность панели не определяется активной вкладкой

`tabs.query({active: true})` возвращает вкладку, активную в момент claim, а не
вкладку-источник запроса. Идентичность разрешается лестницей, где эвристика —
последняя: `port.sender.tab` (если Chrome его даёт) → стабильный per-tab токен
в URL панели, назначенный на lifecycle-событиях → binding окно→вкладка,
записанный при `open()` и сохранённый в `chrome.storage.session` → активная
вкладка, и только если она действительно владеет pending-запросом.

Если ни один шаг не определил вкладку, панель получает `idle`. Claim только по
окну запрещён, поэтому переключение вкладок во время handoff не может
перенаправить запрос, а две панели в одном окне изолированы.

## D-010 — Нулевые runtime-зависимости

Изучены eventsource-parser, fetch-event-source, Floating UI и interact.js.
Нужные подмножества малы, поэтому локальные parser/placement/drag helpers
уменьшают supply-chain поверхность. Подробности и лицензии:
[RESEARCH_NOTES.md](../RESEARCH_NOTES.md).

Playwright остаётся только pinned development dependency для повторяемого
browser smoke; в production ZIP и runtime dependency graph он не входит.

## D-015 — Coverage всегда публикуется вместе со scope

`test:coverage` измеряет 18 перечисленных critical modules, а не весь runtime.
Перед процентами команда печатает include/exclude список, физические line counts
и долю runtime source. Composition roots проверяются отдельно static/browser
tests и не маскируются как покрытые строки.

## D-016 — Production artifact детерминирован

Packager копирует только allowlisted runtime paths во временный staging,
нормализует permissions и timestamp, сортирует все file entries и вызывает
Info-ZIP с отключёнными extra fields. Поддерживаемая reproducible environment —
Ubuntu 24.04, Node 24 и Info-ZIP 3.0; macOS используется как дополнительная,
но не гарантированная среда.

## D-024 — Панель строго tab-specific, глобальный экземпляр не поддерживается

`chrome.sidePanel.open({tabId})` на ненастроенной вкладке может **успешно**
открыть глобальную панель по умолчанию из манифеста. Такой экземпляр выпадает из
tab-scoped протокола: он остаётся привязан к той вкладке, которую обслужил
первой, поэтому запрос из другой вкладки никогда не получает уведомления и
навсегда остаётся pending.

Контроллер проверяет `isConfigured(tabId)` **до** `state.prepare`/`state.replace`,
до `handoff.announce` и до `sidePanel.open()`. Ненастроенная вкладка возвращает
`{status: "not-configured", code: PANEL_NOT_CONFIGURED, retryable: true}` и не
создаёт ни pending-записи, ни binding, ни уведомления, ни вызова провайдера.

Гидрация (`configureAll()`) запускается на инициализации модуля service worker, а
не только в `runtime.onStartup`: это событие срабатывает один раз за сессию
браузера, тогда как worker перезапускается многократно. Её нельзя дожидаться
перед `open()` — это сняло бы user activation. `isConfigured(tabId)` истинно
только после реально принятого Chrome `setOptions()` для текущего стабильного
пути; «configuring» не равно «configured», а ошибка оставляет вкладку
ненастроенной. Параллельные lifecycle-события для одной вкладки разделяют один
in-flight вызов.

## D-025 — Идентичность панели даёт только сам документ панели

Панель может быть привязана к вкладке лишь двумя источниками: `port.sender.tab`
(если Chrome его предоставляет) и стабильный per-tab токен в URL панели.
Третьего источника нет.

Панель без обоих — legacy или глобальный экземпляр. Она не привязана ни к какой
вкладке, никогда не claim'ит tab-scoped запрос, не получает push-уведомлений и
получает типизированную ошибку `PANEL_NOT_CONFIGURED`. Вывод вкладки из window
binding или активной вкладки — ровно то, что позволяло глобальной панели,
открытой для вкладки A, выглядеть панелью вкладки B и «подвешивать» запрос B.

Сохранённый window→tab binding остаётся защитными метаданными (упорядочен и
переживает перезапуск), но никогда не превращает untokenized-панель в
поддерживаемую.
